Jeder Agent bündelt System-Prompt, Modell (inkl. Temperature, Max-Tokens), Tools (jede @Tool-Methode eines Java-Agents wird automatisch registriert), Guardrails (Input/Output), Structured Output (JSON-Schema) sowie Retry-/Timeout-Regeln. Werkzeuge sind nicht nur eingebaut (read/write/grep/bash, Web-Suche), sondern über MCP (QuadToolRegistry-Brücke) und Sub-Agents erweiterbar.

Der Agent-Manager schreibt einen REST-Call auf die AgentDefinition-API – die UI ist bewusst ein Abbild des Java-Modells, kein separater Datenklon.

Workflow-Start & Start-Task

Ein Workflow startet mit einem Start-/Initial-Task (Freitext). Gibt es einen messaging-in-Knoten, ignoriert die Engine den Start-Task und wartet auf eingehende Kanal-Nachrichten. Beim Execute wird der Workflow zuerst persistiert (falls nötig) und dann als Run gestartet – der Run pollt den Status und schreibt die Knoten-Zustände live in den Canvas.

Sicherheit: Guardrails, CapabilityToken, Gate

Guardrails filtern Ein-/Ausgänge je Agent. CapabilityToken bündeln erlaubte Fähigkeiten (Workspace-Lese-/Schreibrechte, Netz, MCP). Das Gate entscheidet an einzelnen Autorisierungs-Punkten synch­ron über Freigabe – Grundlage für HITL und Compliance.

02 Der Workflow Composer

Herzstück der UI: ein ReactFlow-Canvas, auf dem Agent- und Steuerknoten zu einem DAG verbunden werden. Jeder Knoten hat eigene Konfiguration – Zeitüberschreitungen, Bedingungen, Loops, Datenfluss- Mappings zwischen den Schritten, JSON-Ausgabe und Prompt-Vorlagen.

TypZweck
Agentgebundener Agent mit eigenem System-Prompt, JSON-Output, Timeout, Prefix-Optionen
LoopIteration mit Exit-Bedingung (contains:…, iter >= n, matches:…)
ConditionalRouting über contains:…, Regex/Match-Ausdrücke auf dem Output
Fork / Joinparallele Zweige und Aggregation (Join-Policy all)
Asyncfeuer-und-vergiss-Schritte ohne Blockaden im DAG
Nested WorkflowEinschub eines Unter-Workflows inklusive Output-Mapping
Messaging In / OutKanal-Anbindung (Start durch Nachricht / Senden von Ergebnissen)

Loop und Conditional bilden die klassischen quadratischen Bausteine: Eine exitCondition bestimmt, wann ein Loop endet (always, Text-contains, numerisches iter oder matches:<regex>). Ein Conditional routet über true-/false-Referenzen in der Config direkt zum passenden Folgeknoten. Timeouts schreiben einen „Timeout“-Marker in den Output, auf den ein Conditional mit contains:timeout reagieren kann.

Zwischen Schritten werden Input-Mappings definiert: {{nodeId.output}}-Referenzen, Session-Findings (__session.findings, __session.cwd …) und der Start-Task (__initialData). Beim Einfügen eines mittleren Knotens („a‑b → a‑c‑b“) verdrahtet der Composer die Kanten automatisch neu. Nested-Workflow-Knoten mappen Sub-Node-Outputs explizit.

Neu seit dem Caching-Umzug: Jeder Agent-Knoten kennt das Block-A-Prefix (stable System-Präfix für LLM-Cache-Hits). Auf Workflow-Ebene steht ein Schalter „Shared Prefix Caching“ mit Textfeld über dem Start-Task; pro Node lässt sich usePrefix (Workflow-default / an / aus), clearPrefix, ein lokales cachePrefix und eine dynamische prefixSource (inline / URL / Datei / Schritt-Referenz) setzen.

03 Technischer Unterbau

„Funktional“ ist hier nicht flach – jede Funktion hat einen soliden technischen Kern. Drei Themenstränge, jeweils aufklappbar:

Der Kern (quad-core) implementiert das Agent-Modell mit einem ReAct-Loop (AgentRuntime): Thought → Tool-Call → Observation → Antwort. Durch den gesamten Zyklus läuft eine Hook-Pipeline (Inspiration: Interceptor-Pattern) – Guardrails, Telemetrie, Resilience, HITL und GDPR/PII sind austauschbare Haken statt fest verdrahtete Logik. Sub-Agents und Tool-Aufrufe teilen sich den gleichen Laufzeit-Pfad.

Structured Output: Ein JSON-Schema wird über responseFormat an das Modell gereicht; LangChain4j generiert das Schema aus einem Java-Record (@Description, Enums, date/date-time), oder es kommt ein dynamischer JSON-Schema-String (jsonOutputSchema der Workflow-Knoten).

quad-quarkus hostet die Engine mit sieben Node-Executoren (Agent, Loop, Conditional, Fork, Join, Async, Nested, Messaging) und einem DAG-Scheduler. Knoten-Ausgaben fließen über InputBuilder / RunStateWriter; jeder Run trägt einen WorkflowExecutionContext mit Session-State, Findings und dem aktuellen Cache-Prefix. Conditional- und Loop-Pfade werden über Config-Referenzen statt harter Kanten geroutet.

Flyway-Migrationen im gemeinsamen db/migration/common-Ordner plus Dialekt-Overrides (H2/SQLite/PostgreSQL) halten die Schemas synchron; Stores (PersistenceStore, Memory, Workspace, Automation, Skills, Runs, Audit) schreiben über JDBC. Die letzte Migration (V22__workflow_cache_prefix.sql) fügte cache_prefix und prefix_caching zur Workflow-Tabelle hinzu.

React 19 + Vite + vitest; Workflow-Canvas über @xyflow/react (ReactFlow), automatische Mermaid-Diagramme für die Dokumentation, ja-Panel-Editoren pro Knotentyp. Die API-Schicht (types.ts/api.ts) spiegelt die REST-DTOs des Backends – neue Felder wie prefixCaching wandern End-to-End durch Typen, Payload und Persistenz.

04 Besonderheiten dieser Anwendung

Dinge, die man so nicht von jeder Workflow-Box erwartet – zum Ausklappen, jeweils mit technischer Tiefe:

Alle Agent-Nodes eines Runs können sich denselben statischen System-Präfix teilen, damit der Provider-Cache denselben Token-Kopf wiederverwendet – das spart Latenz und Kosten für geteilte Templates (Rollen-Definitionen, Workspace-Regeln, Skills). Die Besonderheit: eine Guard-Schicht erzwingt, dass Agenten mit identischem Präfix auch byte-identische Tools registrieren – sonst würde der Cache stillschweigend degradieren. Das Setup ist als Protokoll + Verifikation umgesetzt:

  • usePrefix je Knoten (Fallback: Workflow-Flag „Shared Prefix Caching“)
  • auflösbare prefixSource: inline, URL, Workspace-Datei, Schritt-Output
  • clearPrefix für Deaktivierung mid-flow
  • Vererbung an Sub-Agents (inheritCachePrefix)
  • Guard: CachePrefixGuard.toolFingerprint pro Präfix-Gruppe
Technik: PromptAssembler platziert das Präfix an Position 0 der System-Nachricht; WorkflowExecutionContext führt einen mutable current prefix, der von Node zu Node wandert.

Strukturierte Antworten werden nicht per Prompt-Gebet erzwungen, sondern per Schema: StructuredOutputConfig generiert aus einem Java-Record ein JSON-Schema (Pflichtfelder via required, Zeiten als format) oder übernimmt einen dynamischen JSON-Schema-String. Der OutputForcer setzt responseFormat (OpenAI-Structured-Output) und hängt bei Bedarf einen Retry-Loop mit StructuredOutputValidator an – ungültige Antworten werden korrigiert statt verworfen.

Für Export/Import von Workflows wird kein JSON-Schema-Verzeichnis-Jar eingebunden, sondern ein eigener deterministischer Schema-Interpreter (QuadWorkflowSchemaValidator): er liest dieselbe quad.workflow.v1.schema.json, die auch das CLI nutzt, wertet aber nur die tatsächlich verwendeten Keywords aus – dieselbe Eingabe ergibt exakt dieselbe Fehlerliste. So bleiben Import-Rejects vorhersagbar und der Validator bleibt leichtgewichtig.

Über die Hook-Pipeline sind Human-in-the-Loop (SSE-basierte Freigabe-Dialoge im HitlOverlay) und Checkpoints angeschlossen. Jede im Fluss kritische Aktion kann an einem Autorisierungs-Punkt stoppen, angereichert mit Kontext für den Menschen – danach geht der Run an derselben Stelle weiter.

Die Suite ist ungewöhnlich breit: Core-Tests (Agent, Builder, Guard, Structured-Output), Snapshot-Tests des Workflow-Kontexts, PrefixSourceResolver- und AgentCachePrefixPropagation-Tests, Quarkus-Integrationstests (inkl. CRUD-Roundtrip mit Prefix-Feldern) und UI-Tests mit vitest/testing-library. E2E-Tests sind als @Tag("e2e") aus dem Default-Lauf aussortiert und laufen gegen ein echtes Backend.

05 Observability & Sicherheit

Runs sind keine Blackbox: Jede Ausführung erzeugt Events (RUN_STARTED, NODE_*, RUN_FAILED …), Step-Timings und einen Audit-Trail. Warum diese Architektur?

Der Kern (quad-core) ist bewusst framework-frei und trägt keine Quarkus-Abhängigkeit – dadurch klappt der Einsatz in klassischen Java-Prozessen ebenso wie in der Quarkus-Runtime. quad-quarkus bringt dann Web-REST, SSE, JDBC-Persistenz und die Workflow-Engine mit. Das UI spricht ausschließlich REST; der Composer bildet das Backend-Modell 1:1 ab, damit neue Fähigkeiten (z. B. Prefix-Caching) mit einer Änderung im DTO-Typ überall ankomme.

Datenfluss eines Runs (vereinfacht)

POST /api/ui/workflows/{id}/execute (oder Messaging-In) → Engine erstellt WorkflowExecutionContext + Run → DAG-Scheduler startet die Root-Knoten → jeder Executor verdrahtet den Agenten (Prompt, Timeout, JSON-Output, Prefix) → Agent läuft im ReAct-Loop mit Tools → Ergebnis an RunStateWriter, Status-Events an den Store → nachfolgende Knoten lesen den Output über Mappings → Run abgeschlossen, Events/AgentEventPublisher melden das Ergebnis, HITL kann zwischenzeitlich unterbrechen.
